# 团队交付分析扩展

> 当问题作用域为"团队交付问题"时，Case Lab和Thinking OS需加载本文件。
> 来源：A+B迭代复盘（2026-07），用户与Codex深度对话后提炼。

## 一、控制权检查（Thinking OS 第二层扩展）

系统思维分析时必须固定追问以下5个问题：

1. **谁承担结果？** — 项目延期、质量问题谁来背？
2. **谁控制过程？** — 谁能决定开发节奏、任务分配、检查节点？
3. **谁拥有资源调度权？** — 谁能加人、换人、调整优先级？
4. **谁可以改变范围、人员和优先级？** — 需求变更谁拍板？
5. **是否存在单点故障？** — 离了谁项目就转不动？

最危险的结构：**结果由你承担，过程由别人控制。**

A+B案例中的典型表现：
- A承担整体交付结果（全量自测、联调、风险兜底）
- 但A无法确保B理解需求、C按时在线、成员完成自测
- A是单点故障——A的时间被生产问题打断，整体进度就下降

## 二、流程有效性检查

任何流程改进动作都要追问：

> 这个动作改变了行为和反馈，还是只是增加了一场会议？

反模式：让BC在评审会上讲自己的部分 → 看起来是"验证理解"，但如果只有口头讲解，没有书面产出、验收标准和检查节点，就只是新的"流程表演"。

流程有效性必须配套以下可验证产物：
1. 书面需求理解（评审后当天提交）
2. 交付边界和依赖项
3. 验收标准
4. 中期可运行版本（开发第2天检查最小链路）
5. 提测前自测确认（各负责人签字，不是A全量自测）

## 三、四类信息强制区分

每次Case Lab分析时必须把内容拆成：

| 类型 | 定义 | A+B案例示例 |
|------|------|-------------|
| 事实 | 发生了什么 | 7.15 E反馈排期不足 |
| 判断 | 我对事实的解释 | BC没有认真理解需求 |
| 假设 | 我假设的因果 | 如果他们认真听讲，问题不会发生 |
| 待验证信息 | 我还没确认的 | 他们当时是否能独立复述需求和验收标准？ |

作用：减少基本归因偏差。把"判断"误当"事实"是团队冲突中最常见的认知错误。

## 四、单环学习 vs 双环学习

- **单环学习**：下次让大家更认真听会、加强提醒 → 改行为不改结构
- **双环学习**：改变评审规则、任务责任、反馈节点和风险升级规则 → 改结构

判断当前处于哪种学习：
- 如果复盘结论是"下次我要更早同步风险" → 单环（改自己的行为）
- 如果复盘结论是"建立风险当天上报机制，满足任一条件即报" → 双环（改系统规则）

双环学习的标志：复盘产出了新的If-Then规则，而不仅是个人决心。

## 五、行动实验设计

每个复盘结论必须转成可验证的实验：

1. **改什么** — 具体改哪个动作/规则/产物
2. **谁负责** — 谁执行这个改变
3. **什么时候执行** — 下次迭代的哪个节点
4. **用什么指标判断有效** — 可观测的信号（不是"感觉变好了"）
5. **失败后如何调整** — 如果指标没改善，下一步怎么调

示例：
> 下次需求评审后，每个负责人当天提交需求理解和验收标准。开发第二天检查最小可运行链路。若仍有大量重复答疑，说明理解验证机制仍无效，需升级为"评审时当场复述+白板画流程"。

## 六、风险升级触发条件

成熟的风险管理不是等根因完全确认后再汇报，而是满足以下任一条件就上报：

- 关键路径上的任务预计延期
- 需要额外人员或加班
- 依赖某个无法替代的人
- 负责人无法联系
- 影响提测、发布或质量目标

> 风险上报不是告状，而是给管理者保留决策时间。你晚一天上报，老板能做的选择就少一天。

## 七、答疑分级机制

| 级别 | 判断标准 | 处理方式 |
|------|----------|----------|
| P0 | 阻塞关键路径、影响多人、今天不解决就延期 | 立即处理 |
| P1 | 影响单个人，有替代方案或当天稍后可处理 | 约定具体时间回复 |
| P2 | 不影响当前开发 | 集中答疑窗口 |

提问者必须带上四项（降低你的答疑成本）：
1. 我理解的需求是什么
2. 我现在采用的方案是什么
3. 我卡在哪里
4. 我建议的两个解决方案是什么

> 核心判断不是"对方觉得紧急"，而是"这个问题是否影响关键路径"。

## 八、推荐书单与案例库（团队交付方向）

按优先级排序，不要同时铺开：

1. **《Team Topologies》** — 团队边界、认知负荷、交互方式、为什么信息都集中到A
2. **《目标》(The Goal)** — 识别项目真正瓶颈，从"谁做得不好"转向"约束在哪里"
3. **《无畏组织》(The Fearless Organization)** — 成员为什么不尽早暴露不确定性
4. **《第五项修炼》** — 补充《系统之美》，强调心智模式和组织学习

社会案例：
- **Toyota Andon（正向）**：一线成员拉绳暴露问题，阻塞即时显性化，不是追责而是触发协作
- **NASA哥伦比亚号（反向）**：风险信息为什么没形成有效决策，小问题为什么被正常化
- **Google Project Aristotle**：团队有效性不只是个人能力，还与结构清晰度、可靠性有关
- **Amazon Working Backwards**：原则如何变成会议、文档、指标和决策规则
