# 案例 001：A+B 迭代中的个人兜底与团队协作失控

## 事件背景

- **迭代周期**：2026-07-10 ~ 2026-07-23
- **需求量级**：中型
- **角色**：后端开发A（用户）、后端开发C（新人）、前端开发B（替换原前端E）、前端负责人E、测试D/F
- **排期**：7.15-7.17开发（后端2人3天+前端1人3天），7.20提测，7.21-7.23测试

## 事件分类

系统问题 + 执行问题（主因为系统问题）

## 关键失控节点

| 节点 | 表面事件 | 深层问题 |
|------|---------|---------|
| 7.10 需求评审 | 大家参加了会议 | 参加不等于理解，缺少理解验证 |
| 7.13 排期 | 各自估时 | 没有计入新人、替换人员、联调和答疑成本 |
| 7.14 技术评审 | A宣讲方案 | 知识集中在A，其他成员没有形成独立交付认知 |
| 7.15 开发 | A同时生成代码、答疑、修生产问题 | A同时承担开发者、架构师、技术支持和项目兜底 |
| 7.15 前端反馈延期 | E发现前端资源不足 | 风险没有当天升级 |
| 7.16-7.18 联调 | A发现大量前端和BC问题 | 测试前置不足，开发自测责任没落到各负责人 |
| 7.18 C失联 | C任务未完成 | 任务责任有名义归属但没有过程检查 |
| 7.20 提测 | A全量自测后提测 | 交付依赖A的最后兜底 |
| 7.21 测试 | 部分问题实为需求变更 | 需求变更与缺陷没有分类机制 |

## Thinking OS 七层复盘

### 第一层：定义问题
- 表象：BC没认真理解需求，导致A被反复打断，项目延期
- 深层：团队没有建立成员独立理解、独立交付、独立暴露风险的机制
- 重新定义：这次迭代为什么没有形成能独立运转的交付系统，反而变成了由A持续理解需求、生成代码、答疑、联调、测试和风险兜底？
- 关键偏差：把"人员问题"放在了"系统问题"之前

### 第二层：系统结构
- 自我强化回路：A越兜底 → BC越少独立承担 → BC独立能力成长变慢 → A越不敢放手 → A越频繁兜底
- 杠杆点：不是换掉BC，而是改变规则（谁负责谁讲解、谁讲解谁写验收标准、谁开发谁先完成自测、风险当天暴露、A只处理关键决策）
- **控制权检查**：A承担整体结果但没有完整的过程控制权——最危险的结构

### 第三层：概率思维
- 计划谬误：把高不确定性事件当确定事件（Codex生成代码基本准确、PRD足够完整、BC能独立开发、不会有生产问题打断）
- 排期应显式包含：理解确认、自测、联调、答疑、返工、风险缓冲、新人onboarding

### 第四层：经济思维
- 资源配置失衡：A把大量时间投入前期文档和技术自评审，但团队缺少的是成员理解验证、任务边界确认、早期联调、风险暴露
- 答疑和兜底成本没有被排期计算——它们不是免费资源

### 第五层：政治与权力
- 有责任无权力陷阱：A承担项目结果责任，但不能确保B理解需求、C按时在线、成员完成自测
- 老板绕过A问E了解前端详情 → 老板开始不信任A的信息完整性
- 向老板反馈时应讲组织事实而非评价个人："当前责任集中在A，但过程控制、风险暴露和成员验收机制不足"

### 第六层：军事思维
- 缺少阶段性小胜利，所有问题堆到7.20前后
- 正确节奏：评审后每人复述理解 → 开发第1天确认接口 → 第2天最小可运行链路 → 提测前1天各负责人自测确认 → 联调前暴露未完成项 → 关键路径延期当天升级
- 核心：把战场前移，把问题前移，把决策前移

### 第七层：元认知
- 过度责任感：把"项目成功"内化成"我必须保证所有人能交付"
- 英雄式救火：用个人能力填坑换取短期进度，牺牲团队长期独立性
- 基本归因偏差：容易把BC问题归为"没听懂"而非"流程没验证理解"
- 准备替代行动：通过完善文档获得确定感，但真正需要验证的是成员能不能独立实现
- **ENFJ深层根因**：兜底不是认知偏差，而是ENFJ身份认同在起作用——"我是那个被需要的人"这个身份比"项目按时完成"更能驱动行为

## 关键判断与修正

### Codex结论的对抗式检查

Codex说"把'我讲过'当成'对方理解了'是本次最核心的认知误差之一"。

修正：这个判断部分正确但掩盖了B和C的个体差异：
- C问的是技术评审中已覆盖的内容 → 系统问题（理解验证缺失），可用"评审后复述需求"解决
- C问的是项目级知识（代码结构、配置） → onboarding缺失，不是评审能解决的
- B可能真的存在能力或态度问题 → 需要管理决策，不是流程改进能覆盖的

正确判断：人员是变量，流程是结构；结构决定问题是否反复，人员决定问题暴露的速度和严重程度。

## 沉淀

### Trigger
当你发现自己同时承担开发、答疑、联调、兜底和风险上报，且忘记同步风险时。

### 反模式
英雄式兜底——通过接管别人工作换取短期进度，制造长期依赖。短期看是责任感，长期看是会自我强化的工作模式。

### 长期原则
- If 承担整体结果 but 无过程控制权 → then 要么争取过程控制权（建立检查点、要求成员汇报、调整任务），要么只承担局部技术责任
- If 要接管别人的工作 → then 先问自己："这是在帮项目，还是在帮我的被需要感？"
- If 风险出现 → then 当天上报，不等"确认根因"——满足任一条件即报

## 下次迭代可执行SOP

### 迭代前
1. 评审会上每个负责人讲自己的部分，不只是A宣讲
2. 评审结束后当天，每个负责人提交：需求理解+交付边界+依赖项+验收标准+风险

### 迭代中
3. 开发第1天结束：每人确认接口已对齐，核心流程跑通
4. 答疑分级：P0即时/P1约定时间/P2集中窗口；提问者必须带上"我的理解+已尝试方案+具体卡点"
5. 开发第2天结束：每人提交进度+未完成项+风险
6. 风险出现当天上报，不等"确认根因"

### 迭代后
7. 提测前1天：各负责人完成自测并确认，不是A全量自测
8. 提测时附"已知问题清单"和"需求变更清单"
9. 有人没按期完成：当天早会暴露，不等联调时发现

### 个人改变
10. 排期时显式算入答疑+联调+返工+生产问题打断，不给纯开发时间
11. Codex生成代码后加"字段约束校验"环节
12. 接管别人工作前问自己："这是在帮项目，还是在帮我的被需要感？"
